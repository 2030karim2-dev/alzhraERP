# خطة تنفيذ تحسين واجهة ERP المحاسبية

**العنوان:** تحسين الكثافة البصرية والاستجابة للهاتف واللوحي وسطح المكتب  
**النطاق:** الواجهة الحالية لتطبيق ERP المحاسبي، مع أولوية مسارات الفواتير والمشتريات والتوريد وجداول الأصناف، ثم المحاسبة والمخزون والتقارير.  
**المبدأ الحاكم:** تحسين واجهة الاستخدام وسرعة الإدخال وكثافة المعلومات دون تغيير منطق الأعمال أو API أو مخطط قاعدة البيانات أو الصلاحيات.

## 1. الهدف التنفيذي

تهدف هذه الخطة إلى تحويل الواجهة الحالية إلى تجربة ERP مهنية عملية، لا إلى نسخة Desktop مصغرة على الهاتف. سيُستفاد من العرض الأفقي على الشاشات الكبيرة، وتُختصر الواجهة على الهاتف، ويُعاد توزيع المكونات عند نقاط التحول بدلاً من الاكتفاء بتصغير الخطوط والأبعاد.

الأولوية التنفيذية هي **وظائف المحاسبة، ثم سرعة الإدخال، ثم كثافة المعلومات، ثم وضوح البيانات، ثم الجماليات**. وستبقى الهوية البصرية الحالية، والألوان، والأيقونات، واللغة العربية، واتجاه RTL محفوظة ما لم يظهر سبب واضح متعلق بقابلية الاستخدام.

## 2. حدود العمل والحماية من الانحدار

### داخل النطاق

يشمل العمل ضبط `width` و`height` و`padding` و`margin` و`gap` و`font-size` و`line-height` و`grid` و`flex` و`breakpoints` وكثافة البطاقات والجداول، إلى جانب إعادة ترتيب تخطيطات الهاتف واللوحي وسطح المكتب، وفصل مكونات الواجهة الكبيرة لتسهيل الصيانة.

### خارج النطاق

لا يجوز تغيير Business Logic أو API أو Database Schema أو أسماء الحقول أو قيمها أو عمليات الحفظ والحساب والضرائب والإجماليات والعلاقات بين الموردين والأصناف والمخزون. ولا يجوز حذف وظيفة أو تجاوز صلاحية أو تغيير سلوك الفواتير من أجل تحقيق شكل بصري أفضل.

| مجال محمي         | قاعدة التنفيذ                                           |
| ----------------- | ------------------------------------------------------- |
| الحسابات والضرائب | لا تغيير في المعادلات أو القيم الناتجة.                 |
| الحفظ والاسترجاع  | لا تغيير في العقود أو ترتيب البيانات أو حالات العمليات. |
| الصلاحيات         | لا تغيير في الحراسة أو الأدوار أو نطاق الشركة/الفرع.    |
| البيانات          | لا حذف أو ترحيل أو إدخال تجريبي أثناء تحسين الواجهة.    |
| الهوية            | الحفاظ على الألوان والنمط والأيقونات وRTL.              |

ستُستخدم هذه المقاسات كنقطة بداية، ثم تُضبط بناءً على المحتوى الفعلي وكثافة الشاشة. لا تُطبق آلياً على كل مكون إذا أضرّت القراءة أو اللمس.

## 4. نقاط التحول والتخطيطات

ستبدأ المراجعة من نقاط التحول الموجودة في المشروع، ثم تُوحّد عند الحاجة حول التقسيم التالي:

| النطاق        |        العرض | السلوك المطلوب                                                                               |
| ------------- | -----------: | -------------------------------------------------------------------------------------------- |
| Mobile        |      0–639px | كثافة عالية، تخطيط عمودي مختصر، إجراءات ثانوية داخل قائمة أو Sheet، وعدم فرض جدول أفقي كامل. |
| Tablet        |   640–1023px | Grid مرن، صفوف حقول من حقلين عند كفاية العرض، واستخدام العرض المتوسط بكفاءة.                 |
| Desktop       | 1024px فأعلى | استغلال العرض الأفقي لإظهار بيانات الفاتورة والجدول والإجماليات معاً.                        |

## 5. مراحل التنفيذ

### المرحلة الأولى: التدقيق والجرد

يبدأ التنفيذ بجرد الصفحات والمكونات المشتركة والـhooks ومسارات الإدخال المرتبطة بالمشتريات والفواتير والمخزون والمحاسبة والتقارير. تُقاس أحجام الملفات، وتُحدد البطاقات والأزرار والجداول والـheaders التي تكرر نفس النمط، وتُسجل نقاط التكرار قبل أي تعديل.

المخرجات المطلوبة هي خريطة للصفحات ذات الأولوية، وقائمة بالمكونات المرشحة لإعادة الاستخدام، وتقرير بالمشكلات المرئية، وقائمة بالوظائف الحساسة التي يجب عدم المساس بها.

### المرحلة الثانية: تأسيس نظام الكثافة

تُعرّف قيم مشتركة للكثافة والمسافات والارتفاعات وأحجام النصوص، إما عبر tokens أو أصناف CSS/utility موجودة في المشروع، مع تجنب إدخال قيم متفرقة داخل كل صفحة. تُراجع البطاقات والحقول والأزرار والجداول لتستخدم النظام المشترك.

سيُحافظ النظام على الفرق بين الإجراء الأساسي والثانوي وأيقونات الإجراءات، وعلى حالات التركيز والتمييز والرسائل والتحميل والفراغ والخطأ.

### المرحلة الثالثة: الهيدر والتنقل وأشرطة الإجراءات

يُحوّل Header الهاتف إلى بنية Compact تحافظ على زر القائمة واسم النظام والحساب والإشعارات وحالة النظام والقسم الحالي دون تكديس أشرطة أفقية كبيرة. يبقى Bottom Navigation متاحاً للهاتف بحجم قابل للمس والوصول بالإبهام، بينما تستخدم الشاشات الكبيرة Sidebar أو التنقل المناسب دون تكرار غير ضروري.

في قسم إدارة المشتريات والتوريد يكون إجراء **فاتورة جديدة** هو Primary، ويظهر سجل التوريد ومرتجعات الموردين وعروض الأسعار والتحليلات والاستيراد الذكي كإجراءات ثانوية أو ضمن قائمة حسب المساحة.

### المرحلة الرابعة: نموذج الفاتورة

تُعاد صياغة بيانات الفاتورة إلى Grid مضغوط. على الهاتف تُعرض الحقول بعرض كامل عند الحاجة، وتُجمع الحقول في صفين عندما تسمح المساحة، مثل التاريخ ورقم الفاتورة، ونوع الفاتورة والعملة، والمستودع والصندوق/البنك. تُصغّر المسافة بين label وinput، وتُمنع البطاقات المنفصلة عندما لا تضيف فصلاً وظيفياً.

يجب اختبار النموذج مع إدخال لوحة المفاتيح والتنقل بالـTab واللمس، ومع حالات النص العربي الطويل والقيم الرقمية وأخطاء التحقق.

### المرحلة الخامسة: جدول الأصناف

يُعامل جدول الأصناف باعتباره أهم مساحة للإدخال. على Desktop يستهدف ارتفاع صف 40–46px، وعلى الهاتف 42–48px مع إبراز الخلايا القابلة للتحرير وتقليل padding داخل الخلايا.

على الهاتف تُعرض الأعمدة الأساسية: الصنف، الكمية، السعر، الإجمالي. أما رقم القطعة والشركة المصنعة والخصم والضريبة والملاحظات فتظهر عبر Expand Row أو Bottom Sheet أو تفاصيل الصف. لا يُفرض تمرير أفقي مزعج على فاتورة بسيطة، ولا تُحذف أي معلومة؛ بل تُنقل إلى مستوى تفصيلي مناسب.

### المرحلة السادسة: بقية المحاسبة والمخزون والتقارير

بعد تثبيت نموذج الفاتورة، تُطبق قواعد الكثافة على صفحات المحاسبة والتقارير والمخزون والديون والتحصيل ولوحات التحكم ذات الصلة. ستُراجع المسافات البيضاء والبطاقات الكبيرة والحقول والأزرار والجداول، مع إعادة استخدام المكونات المشتركة بدلاً من نسخ التنسيقات.

تُرتب الأولويات حسب الاستخدام اليومي وحجم الأثر، وليس حسب سهولة التعديل فقط. ولا تُجرى تغييرات متوازية على ملفات مترابطة دون فحص بعد كل مجموعة صغيرة.

## 6. معايير إمكانية الوصول وقابلية الاستخدام

يجب أن تبقى جميع العناصر التفاعلية قابلة للوصول باللمس ولوحة المفاتيح، مع وجود focus واضح، وتسميات عربية مفهومة، و`aria-label` للأيقونات التي لا تحتوي نصاً، وحالات تحميل وخطأ وفراغ واضحة. لا يجوز أن يؤدي تصغير المكونات إلى أهداف لمس ضيقة أو نص غير مقروء.

يجب الحفاظ على اتجاه RTL في ترتيب الحقول والأزرار والقوائم والجداول، مع التحقق من اتجاه الأرقام والقيم المالية دون خلط بصري بين النص العربي والأرقام.

## 7. منهجية التنفيذ الآمن

سيُنفذ العمل على دفعات صغيرة. كل دفعة تبدأ بتسجيل البند في `todo.md`، ثم تعديل محدود، ثم تشغيل ESLint وTypeScript المجزأ واختبارات الوحدة الخاصة بالمسار. بعد نجاحها تُراجع الفروقات والتنسيق، ثم تُحفظ نقطة استقرار قبل الانتقال إلى دفعة أكبر.

لن تُنفذ تغييرات قاعدة بيانات أو migrations لأن المطلوب واجهة وكثافة فقط. كما لن تُستخدم بيانات وهمية أو تقييمات أو مراجعات مصطنعة لاختبار الواجهة؛ ستُستخدم حالات موجودة أو fixtures اختبارية غير معروضة كمحتوى إنتاجي عند الحاجة.

### معايير النجاح

تُقبل كل صفحة بعد التأكد من عدم وجود overflow أفقي غير مقصود، وعدم تداخل أو قص النصوص المهمة، وعدم خروج الأزرار من الشاشة، وعدم اختفاء أي وظيفة، وبقاء حقول الإدخال سهلة اللمس، وبقاء الأرقام واضحة، وقدرة المستخدم على الوصول إلى الإجراء الأساسي بسرعة.

ستُجرى اختبارات تفاعل للفواتير تشمل فتح فاتورة جديدة، اختيار المورد، إدخال التاريخ والرقم، إضافة صنف، تعديل الكمية والسعر، إظهار التفاصيل الثانوية على الهاتف، الحفظ، الطباعة أو التصدير إن كانا متاحين، والتأكد من أن النتائج والحسابات لم تتغير.

كما ستُشغل اختبارات Vitest، وESLint لملفات الإنتاج، وTypeScript المجزأ، وفحوصات `git diff --check`. فشل اختبار خارج نطاق الواجهة سيُسجل منفصلاً ولن يُخفى، ولن يُنسب إلى التغييرات دون دليل.

## 9. مؤشرات القياس قبل وبعد

ستُقاس كثافة الشاشة بعدد الصفوف أو الحقول المفيدة الظاهرة في أول viewport، وارتفاع Header وtoolbar، وعدد التمريرات اللازمة للوصول إلى الإجراء الأساسي، ومقدار overflow، وعدد البطاقات المتكررة، ووضوح الجدول على الهاتف.

لا يُعتبر تقليل الارتفاع نجاحاً إذا نتج عنه قص أو صعوبة لمس أو انخفاض وضوح. المعيار هو تقليل المساحة المهدرة مع بقاء الإدخال سريعاً وآمناً.

## 11. ترتيب التنفيذ المقترح

يُنفذ العمل بالترتيب الآتي: الجرد، ثم tokens والكثافة، ثم الهيدر والتنقل، ثم شريط إجراءات المشتريات، ثم نموذج الفاتورة، ثم جدول الأصناف، ثم المحاسبة والمخزون والتقارير، ثم التحقق الشامل والتوثيق. لا يُنصح ببدء تحسين كل الصفحات دفعة واحدة؛ الأفضل استخدام الفاتورة كنموذج مرجعي ثم نشر القواعد على الصفحات المتشابهة.

## 12. تعريف الإنجاز النهائي

يُعد المشروع جاهزاً للمراجعة عندما تكون صفحات الأولوية متجاوبة على المقاسات السبعة، وتظهر الواجهة بكثافة مناسبة دون فراغات مهدرة، ويعمل إدخال الفاتورة وجدول الأصناف على الهاتف دون تمرير مزعج، وتحافظ كل الوظائف والصلاحيات والحسابات على سلوكها، وتنجح فحوصات الإنتاج والاختبارات الخاصة بالمسارات المعدلة، ويكون كل تغيير موثقاً في `todo.md` وملف التدقيق.

أي ملاحظة لا يمكن التحقق منها بسبب اختلاف مشروع WebDev النشط أو ضغط الذاكرة ستُسجل كقيد صريح، ولن تُعرض على أنها نجاح غير مثبت.
